# Agente: Backend de Validación de Autenticación de Correo

## Comunicación

* Responder siempre en español, directo y sin rodeos.

## Reglas de código

* Cada función/método lleva un docstring de una línea.
* `app.py` solo define rutas y arma la respuesta — la lógica de negocio va en `services/`, los helpers puros (sin Flask/checkdmarc/dkimpy) van en `utils/`.
* **Nunca editar, agregar ni eliminar datos de la base de datos** (filas, columnas, tablas, migraciones, `INSERT`/`UPDATE`/`DELETE`, scripts de limpieza) sin autorización explícita del usuario, ni en local ni en producción. Preguntar y esperar confirmación antes de tocar la base real.
* No duplicar lógica ya resuelta por `checkdmarc`, `dkimpy` o `parsedmarc`. `dkimpy` es la única responsable de todo lo de DKIM. Mantener la arquitectura desacoplada: cualquiera de estas libs debe poder sustituirse sin afectar el resto.

## Arquitectura

* `app.py` — rutas Flask, delega a `services/`.
* `services/checkdmarc_service.py` — corre `checkdmarc` + DKIM (`dkimpy`) + arma instrucciones DNS para monitoreo.
* `services/card_builder.py` — arma las "cards" (ok/warn/fail) y los riesgos priorizados.
* `services/monitoring_service.py`, `reports_service.py`, `notifications.py` — alta/estado de dominios monitoreados, ingesta de reportes DMARC, alertas por correo.
* `services/auth_service.py` — registro/login/actualización de cuenta.
* `services/pdf_service.py` — generación de PDF (ReportLab).
* `utils/` — helpers puros (`domain_validation.py`, `formatting.py`, `dmarc_builder.py`, `pagination.py` — `paginate()`, un solo helper compartido por toda tabla filtrable/paginada, ver sección de esa feature más abajo —, `serializers.py` — Fase 1 del plan de API en `API_PLAN.md`: una función `serialize_x(obj)` por modelo, sin lógica de negocio, solo transformación de campos a dict listo para `jsonify()`; nunca expone `password_hash`/`api_key_hash` de `User`).
* `models/` — `db = SQLAlchemy()`, modelos en `monitoring.py`/`user.py`. Persistencia en Postgres.
* `jobs/recheck_domains.py` — vigilancia DNS periódica, programada con APScheduler dentro del mismo proceso web (`start_scheduler()` en `app.py`), no un Railway Cron aparte.
* `jobs/deactivate_expired_trials.py` — mismo patrón/scheduler que el anterior; desactiva dominios de usuarios cuyo plan venció sin renovarse (ver sección de planes más abajo).

## Frontend

* Interactividad vía [htmx](https://htmx.org/), no JS manual (fetch + DOM a mano). El servidor responde con fragmentos HTML (`templates/partials/`) a las rutas que consume htmx — JSON solo en `/api/...`. Preferir `hx-on:`/`hx-*` declarativo antes que sumar un `.js` nuevo.
* Todo botón/link estilizado como botón lleva un ícono SVG inline (`stroke="currentColor"`), sin librerías de íconos externas.
* **Layout con sidebar** (`templates/layout.html` + `partials/sidebar.html`/`topbar.html`): toda página autenticada nueva debe usar `{% extends "layout.html" %}` (bloques `title`/`head_extra`/`body_class`/`content`), no un `<html>` completo propio. Excepción a propósito: `auth/login.html`/`auth/register.html` (pantalla completa sin nav, antes de loguearse no hay nada que navegar).
* El checkbox `#sidebar-toggle` debe ser **hermano directo** del `<aside>` (mismo nivel del DOM) — `peer-checked:` de Tailwind solo alcanza hermanos, no ancestros/descendientes.
* Ítem activo del nav/sidebar: comparar contra `request.endpoint`, nunca contra la URL (sobrevive a un rename de ruta).
* **Tema**: fondo `#fcfaef`, tarjetas blancas, tipografía "Plus Jakarta Sans" (clase `.font-jakarta` en `home.css`, no arbitrary-value de Tailwind) en todo el sitio, incluidas `auth/login.html`/`register.html`. Color primario único: **`#2d2147`** (botones, hovers, nav activo, foco de inputs, logo) — no queda ningún otro accent color en la app (el rosa `#ef5184` y el gris `#474545` anteriores fueron retirados por completo). Si se ajusta el tema, revisar también `STATUS_META`/`RISK_SEVERITY`/`score_color` en `card_builder.py` (colores de estado ok/warn/fail, independientes del accent). El PDF (`pdf_service.py`) es 100% independiente de estas clases Tailwind.
* **Regla: nunca usar `border border-zinc-200` ni `shadow-sm`/`shadow-md`** — ninguna sombra ni borde gris neutro para separar tarjetas del fondo; el contraste `bg-white` contra el fondo `#fcfaef` ya alcanza. Para hover en elementos interactivos, usar un borde de color sólido (ej. `border border-transparent hover:border-[#2d2147]`). Bordes de color (`border-emerald-200`, `border-[#2d2147]/60`, etc.) sí se mantienen. Excepciones:
  * `.verify-btn`: necesita `border-transparent` (no omitir `border`) porque `home.css` le pinta `border-color` con `!important` mientras dura el POST — sin ancho de borde esa animación no tiene contra qué animar.
  * Inputs de texto: `border border-zinc-200` en reposo (sin sombra) + `focus:border-[#2d2147]/60` — patrón ya validado, no reintentar `shadow-md` en foco ni `border-transparent` en reposo (ya descartados).
* Tamaño de letra: el texto chico (`text-[9px]` a `text-[13px]`, `text-xs`/`text-sm`) tiene overrides `!important` en `home.css` (+2px). Un tamaño arbitrario nuevo en ese rango necesita su propia regla ahí o queda más chico que el resto.
* Pace.js (barra de progreso) en toda página completa: `window.paceOptions` se define antes de cargar `pace.min.js`.
* **`html { scrollbar-gutter: stable; }`** (en `home.css`, regla global): sin esto, una página cuyo contenido cruza la altura de la ventana muestra scroll vertical y le resta ~15px de ancho, mientras que una página más corta no lo muestra y usa el ancho completo — como los contenedores van centrados (`mx-auto`), eso los corre unos píxeles entre un estado y otro (se notó al activar/desactivar un dominio: el dashboard inactivo tiene una caja extra y se sentía "saltar" respecto al activo). No revertir esta regla.
* **Ancho de contenedor por página** (`max-w-* mx-auto px-6 py-16` en el `<div>` raíz de cada página): **un solo tamaño, `max-w-5xl`, para toda página que extiende `layout.html`** — sin excepción, sea formulario de una columna o tabla ancha. Se unificó a pedido explícito del usuario ("para que sea más uniforme") después de que el esquema anterior de dos tamaños (`max-w-4xl` para formularios, `max-w-5xl` para contenido ancho) generara un error de documentación real: una página quedó listada en ambos buckets a la vez tras una migración de `max-w-4xl` a `max-w-5xl` sin sacarla de la lista vieja. **No volver a introducir `max-w-4xl` ni ningún otro tamaño en el contenedor raíz de una página nueva** — si una página nueva necesita verse más angosta, usar `max-w-*` en un elemento interno (ej. un párrafo con `max-w-2xl`), nunca en el `<div>` raíz. Única excepción real: `auth/login.html`/`auth/register.html`, que no extienden `layout.html` (son standalone, layout split-screen a propósito) y no llevan esta clase en absoluto.
* **Toasts/alertas**: [nextjs-toast-notify](https://www.nextjstoastnotify.com/) — CDN pinneado a una versión real y confirmada (`unpkg.com/nextjs-toast-notify@1.62.0/...`, verificar con `curl -o /dev/null -w "%{http_code}"` antes de cambiar la versión: una versión que no existe da 404 y `showToast` queda `undefined` sin ningún error visible en la página, solo en la consola del navegador — así se rompió la primera vez). Cargado en `layout.html` (todas las páginas del tema claro) y también en `auth/login.html` (solo para el toast de "credenciales incorrectas") — `auth/register.html` todavía no lo necesita. Toda alerta flotante nueva (éxito, error, advertencia, info) usa esta librería, nunca un `alert()` nativo ni un div armado a mano. API global `showToast.<tipo>(mensaje, opciones)`:

  ```js
  showToast.success("Dominio registrado — ya podés configurar el DNS.", {
    duration: 5000, position: "top-right", transition: "swingInverted", icon: "", sound: true,
  });
  ```

  Tipos: `success` / `error` / `warning` / `info`. Opciones consistentes en toda la app (no cambiarlas sin razón, para que no se sienta distinto cada toast): `duration: 5000`, `position: "top-right"`, `transition: "swingInverted"`, `icon: ""` (sin ícono default), `sound: true`. Tres formas de disparar el toast, según cómo responde la ruta — usar la que corresponda, no inventar una cuarta:
  1. **`render_template()` directo** (form POST sin redirect ni htmx, ej. `auth/account.html`, `monitoring/registered.html`): `<script>` dentro de `{% block head_extra %}`, condicionado con Jinja (`{% if error %}`/`{% if just_registered %}`), envuelto en `DOMContentLoaded`.
  2. **`redirect()`** (poco común en esta app; preferir htmx si se puede evitar la recarga): esta app no usa `flash()` de Flask, así que el mensaje viaja como query param en la URL del redirect, la ruta destino lo lee con `request.args.get(...)` y dispara el toast igual que el caso 1.
  3. **htmx** (`hx-post`/`hx-swap`, sin recargar la página — preferido cuando aplica, ver regla de htmx más arriba): la ruta devuelve el fragmento normal y agrega el header `HX-Trigger` con un JSON (`response.headers["HX-Trigger"] = json.dumps({"showToast": {"message": "..."}})`); un listener ya registrado en la página (`document.body.addEventListener('showToast', ...)`, dentro de `{% block head_extra %}`) dispara el `showToast.*` real con el mensaje del evento. Ejemplo real: `monitoring_toggle` (activar/desactivar un dominio, `templates/partials/monitoring_toggle_status.html` + el listener en `templates/monitoring/dashboard.html`).

## Checker de un dominio (`/`, `POST /check`, `GET /api/check/<domain>`)

* DKIM: `checkdmarc` no lo reporta — se prueba una lista de selectores comunes con `dkimpy`, más `?selector=` opcional. `check_dkim()` los prueba en paralelo (`ThreadPoolExecutor`), no en serie — un selector inexistente puede tardar varios segundos en responder según el proveedor de DNS del dominio (visto en producción: ~5.4s por selector en un dominio real), y en serie con ~10 selectores comunes eso sumaba hasta casi un minuto por dominio. Si se agrega un selector nuevo a `COMMON_DKIM_SELECTORS`, sigue siendo seguro en paralelo (cada selector es una consulta DNS independiente, sin estado compartido).
* Ausencia vs. falla: para MTA-STS/TLS-RPT/BIMI (`SOFT_ABSENCE_KEYS`), que el registro no exista es ADVERTENCIA, no FALLA (protocolos opcionales, a diferencia de SPF/DMARC).
* Timeouts de DNS → siempre `na` (N/D), nunca FALLA; no afectan el `score`.
* Nuevos tags/mecanismos DMARC o SPF a traducir van en los diccionarios de `card_builder.py` (`DMARC_POLICY_LABELS`, `SPF_MECHANISM_LABELS`, etc.), no hardcodeados en la plantilla.
* SPF sin registro: nunca sugerir un valor final (podría rechazar correo legítimo) — solo mostrar los hostnames MX reales y, si matchea un proveedor conocido, un `include:` de partida.
* Resumen con IA (`services/ai_summary.py`) es opcional: sin `OPENAI_PROJECT_API_KEY` o si falla/tarda, no se muestra y el resto sigue funcionando. Solo en el flujo HTML, nunca en `/api/check/<domain>`.
* PDF (`GET /reporte-pdf?domain=...`): ReportLab (no WeasyPrint, exige libs de sistema no disponibles en Railway/Windows sin config extra). `pdf_service.py` arma el documento a mano a partir del mismo contexto que `build_result_context()` — un `kind` de tarjeta nuevo en `card_builder.py` necesita su rama en `_card_content()` o sale vacía en el PDF. `ParagraphStyle` no hereda `leading` de `fontSize` (>10pt necesita `leading` explícito). Tablas anidadas dentro de una caja deben dimensionarse contra `width - 2*CARD_PAD`, no el ancho total de página.
* Botón de descarga de PDF: `fetch` → blob → `<a download>` sintético (`downloadPdfReport()` en `partials/pdf_download_script.html`) para poder deshabilitar el botón durante la generación — incluir ese partial en vez de duplicar la lógica.

## Monitoreo continuo de DMARC

* **Vigilancia DNS** (`jobs/recheck_domains.py`): compara contra el último `DomainSnapshot`, genera `Alert` si cambió política DMARC/SPF/selectores DKIM. Se dispara sola vía `start_scheduler()` (APScheduler, `BackgroundScheduler`) desde `app.py` — cada `RECHECK_DOMAINS_INTERVAL_HOURS` horas (default 12), corriendo dentro del mismo proceso web, no como servicio/cron aparte. Sólo arranca en `if __name__ == "__main__"` (nunca al importar `app` para tests) y sólo una vez si el reloader de Flask está activo (`WERKZEUG_RUN_MAIN`). **Requiere una sola instancia** del servicio — con réplicas, el job correría duplicado una vez por instancia.
* **Vigilancia de tráfico real** (`services/reports_service.py`): ingiere reportes agregados vía [parsedmarc](https://github.com/domainaware/parsedmarc) (webhook), compara remitentes reales contra el SPF declarado, genera `Alert` tipo `unknown_sender`.
* **Reportes forenses / RUF** (`services/forensic_reports_service.py`, modelo `ForensicReport`): paralelo a lo anterior pero para reportes individuales por mensaje (no el agregado diario). parsedmarc los llama internamente "failure reports" desde su v10 (`ForensicReport`/`forensic_url`/`save_forensic` son alias de compatibilidad de `FailureReport`/`failure_url`/`save_failure` — usar los nombres nuevos). Webhook: `POST /webhooks/dmarc-forensic/<secret>`, mismo `DMARC_WEBHOOK_SECRET` que el de agregados (mismo secreto, distinto path — no hay una env var separada). El payload es un objeto plano por mensaje (no records anidados como el agregado).
  * **Decisión de retención/PII, no reabrir sin pensarlo de nuevo**: el payload de parsedmarc trae `sample`/`parsed_sample` con el correo original **completo** (cuerpo, cabeceras, adjuntos con hash). Eso nunca se persiste — `ingest_forensic_report()` sólo guarda metadata de triage (asunto, `message_id`, remitente/destinatario, IP/ASN de origen, resultado de la validación, si la muestra vino con o sin cuerpo). Guardar el correo completo de terceros sin necesidad es una responsabilidad de datos que no se asumió a propósito.
  * Es normal que no llegue ninguno: varios proveedores grandes (Gmail, Yahoo) dejaron de mandar RUF por privacidad — el dashboard ya avisa esto en el texto de la sección, no tratarlo como bug si la lista queda vacía.
  * Se muestran en `templates/monitoring/dashboard.html` (sección "Reportes forenses (RUF)", debajo de los reportes agregados). **No** están incluidos todavía en `pdf_service.py` ni en `/tendencias` — alcance dejado afuera a propósito, agregarlo si se necesita.
  * El worker de `parsedmarc` ya desplegado en Railway (ver README, sección `config/parsedmarc.ini`) necesita que se le agregue `save_failure`/`failure_url` (o las env vars `PARSEDMARC_GENERAL_SAVE_FAILURE`/`PARSEDMARC_WEBHOOK_FAILURE_URL`) para que estos reportes empiecen a llegar — sin ese cambio operativo en el worker, el modelo/ruta/UI ya están listos pero no va a llegar nada.
* `detect_unknown_senders()`: comparar tanto substring directo (nombres de ASN cortos) como la palabra clave del dominio base del target vs. las palabras del nombre de organización (nombres largos no son substring literal) — evita falsos positivos ya vistos en producción.
* `Alert.kind_label`/`KIND_LABELS` (`models/monitoring.py`): un `kind` nuevo necesita su entrada ahí o se muestra crudo en inglés.
* Activar/desactivar (`is_active`): pausar, nunca eliminar — reversible, conserva historial.
* **Límite de dominios por plan** (`models/user.py:UserPlan`, `services/monitoring_service.py:get_max_domains()`/`count_active_domains()`): cada usuario puede tener a lo sumo `max_domains` dominios con `is_active=True` al mismo tiempo — desactivar uno libera un cupo (el límite es "en uso ahora", no "registrados alguna vez"). Un usuario sin fila propia en `UserPlan` no está "sin plan": usa `DEFAULT_MAX_DOMAINS` (1). `get_max_domains()` lee siempre `UserPlan.max_domains`/`expires_at` directo (nunca el catálogo en vivo) — son los campos que de verdad se hacen cumplir.
* **Catálogo de planes** (`models/user.py:Plan`, tabla `plans`): **la decisión anterior era explícitamente NO tener catálogo** ("un solo número por usuario") — se revirtió a pedido del usuario cuando pidió planes reales con nombre/precio/trial. Hoy son 2 filas fijas, sembradas a mano una sola vez (`name`/`label`/`max_domains`/`price_usd`/`trial_days`): `"free"` (1 dominio, USD 0, 20 días de prueba) y `"paid"` (5 dominios, USD 12, sin vencimiento). Sin self-service para crear un tercero — se agrega con una fila más, a mano.
  * **Todavía NO hay cobro real** — sin pasarela integrada a propósito (decisión explícita: se dejó la pasarela para una vuelta aparte, es un proyecto bastante más grande — cuenta de Stripe o similar, checkout, webhooks, renovación). `Plan.price_usd` es sólo informativo. Pasar a `"paid"` hoy es 100% manual: el admin aprieta un botón en `/admin/usuarios/<id>/plan` después de que la persona pague por otro medio (transferencia, etc.).
  * **`assign_plan(user_id, plan_name)`** (`monitoring_service.py`): asigna un plan del catálogo — copia `max_domains` y calcula `expires_at` (`ahora + trial_days` si el plan lo tiene, `None` si no). Se llama en dos lugares: `register_user()` (`auth_service.py`, siempre `"free"`, automático en cada alta nueva) y el botón "Asignar Free/Pago" del admin. **Distinto de `update_user_plan()`** (el ajuste manual de número+fecha, para una excepción puntual que no corresponde a ningún plan del catálogo) — este último limpia `UserPlan.plan_id` a `None` a propósito, para no mentir mostrando un plan del catálogo que ya no aplica.
  * **`UserPlan.plan_id` es nullable y puede quedar `None`** — asignaciones manuales/viejas, de antes de que existiera el catálogo (ej. un usuario real ya tenía `max_domains=3`/`expires_at` custom antes de este cambio: se migró dejando `plan_id=None`, sin tocar sus números — la UI lo muestra como "Personalizado (sin plan del catálogo)", no como un error).
  * **`jobs/deactivate_expired_trials.py`** (mismo patrón que `recheck_domains.py`, programado en `start_scheduler()` cada `CHECK_TRIALS_INTERVAL_HOURS`, default 6): a diferencia de `get_max_domains()` (que sólo bloquea *agregar* dominios nuevos cuando el plan ya venció, sin tocar los que ya estaban activos), este job sí **desactiva de verdad** los dominios de cualquier usuario no-admin con `UserPlan.expires_at` vencido — es la pieza que hace que el trial Free se sienta como "se apaga solo", no solo "no podés sumar más". Reversible: reactivar un dominio vuelve a pasar por el chequeo de límite normal.
  * **Los administradores no tienen límite**: `get_max_domains()` devuelve `None` para cualquier `is_admin=True`, sin importar su `UserPlan` — quien administra la herramienta no necesita un plan para usar su propia cuenta (si no fuera así, con el default en 1, el admin real ya hubiera quedado bloqueado el día que se bajó el default de 3 a 1, teniendo varios dominios propios). **Todo caller de `get_max_domains()` debe tratar `None` como "sin límite"** (`if limit is not None and count >= limit`), nunca comparar `None` directo con `>=` (`TypeError` en Python). La UI también lo refleja: columna "Plan" muestra "Ilimitado" en vez de un número, y el formulario de editar plan (`admin/edit_plan.html`) avisa que no tiene efecto mientras la cuenta sea admin (el valor se guarda igual, por si algún día deja de serlo).
  * Se hace cumplir en **dos lugares**, no uno: `register_domain()` (alta nueva o reactivación de un dominio pausado) y `set_active()` (el botón Activar del dashboard) — si sólo se chequeara en el alta, alguien podría desactivar un dominio y reactivar cualquier otro sin pasar por el límite.
  * `register_domain()` devuelve `(monitored, created, error)` — `error` es `None`, `"other_user"` (dominio de otra cuenta) o `"limit_reached"`; distinguir estos dos casos es necesario porque cada uno muestra un mensaje distinto en `/monitoreo`. `set_active()` devuelve `(monitored, error)` — `monitored` viene con los datos sin cambiar (no `None`) cuando `error="limit_reached"`, para poder seguir mostrando el fragmento del dashboard con el toast de error (patrón 3 de toasts, `partials/monitoring_toggle_status.html`).
  * Dominios sin dueño (`MonitoredDomain.user_id` nulo, legado de antes del login) no tienen plan que hacer cumplir — `set_active()` los activa sin chequear límite.
* Generador de política DMARC (`utils/dmarc_builder.py`): vista previa, no se persiste. `p`/`pct`/`adkim`/`aspf` siempre arrancan conservadores (`p=none`, `pct=25`, `adkim=r`, `aspf=r`) sin importar la política real ya publicada — decisión explícita del usuario, riesgo asumido a propósito. `sp`/`rua`/`ruf` sí respetan el valor real si ya existe.
* MAX_REPORT_RECORDS=30 en el PDF del dashboard: sin este tope, un reporte real grande revienta el layout (`LayoutError`) — se recorta y se avisa cuántos quedaron afuera, nunca en silencio.
* **Remitentes reales del dashboard** (`templates/partials/domain_senders_table.html`, incluido desde `monitoring/dashboard.html`): tabla agrupada por IP (`list_domain_senders()` en `monitoring_service.py`), no una fila por reporte donde reapareció esa IP — antes las cards mostraban la misma IP repetida en cada informe donde aparecía (un remitente recurrente puede aparecer en decenas de informes). Agregado en SQL (`GROUP BY source_ip`), con filtros `rango` (7d/30d/90d/todos), `estado` (todos/con_fallas, post-agregación en Python — ya son remitentes únicos, no records crudos) y `q` (organización o IP), paginada igual que Informes DMARC.
  * **Filtros por htmx, no recarga de página** (a pedido explícito): el `<form id="senders-filters-form">` es el mismo patrón ya usado en el generador de política DMARC (`monitoring/registered.html`) — `hx-trigger="change, input delay:300ms"` sobre el form entero, pills como `<input type="radio" class="peer sr-only">` + `<span class="peer-checked:...">` (no `<a href>`), apuntando a `GET /monitoreo/<token>/remitentes` (ruta nueva, sólo devuelve el partial). Paginación: botones (no `<a>`) con `hx-include="#senders-filters-form"` (para mandar los filtros actuales) + `hx-vals` con el número de página (que pisa cualquier `page` del form) — sin esto, "Siguiente" perdería el filtro/búsqueda activos.
  * **`get_dashboard_data()` no cambió** — sigue devolviendo la lista cruda de `AggregateReport` (`reports`) porque el PDF (`pdf_service.build_dashboard_pdf_bytes`) y el botón de activar/desactivar (`partials/monitoring_toggle_status.html`, chequea `{% if reports %}`) siguen dependiendo de esa forma; `list_domain_senders()` es una consulta aparte, sólo para esta tabla.
  * **Gotcha de Jinja**: la clave `"items"` de un dict paginado (mismo nombre que ya usa `list_dmarc_reports()`) choca con el método `dict.items()` — Jinja resuelve `foo.items` como `getattr()` antes que `foo['items']`, así que nunca cae al valor real. En `dmarc_reports.html` no pasa porque `items` se pasa como variable de nivel superior (`**data`, no como atributo de un dict); en este partial sí pasa porque `senders` se pasa entero como un solo dict — se resuelve con `senders['items']`/`senders['total_items']`/etc. (corchetes) en todo el partial, no `senders.items`.
  * **`estado=con_fallas`/`sin_fallas` se define sobre `dmarc_aligned`, no sobre `spf_aligned`/`dkim_aligned` por separado**: DMARC pasa si SPF **o** DKIM alinea (es la definición del estándar), así que un remitente con SPF roto pero DKIM siempre alineado (ej. Zoho relayeando, típico) nunca falló DMARC de verdad y debe caer en "sin fallas" aunque su columna SPF muestre 0% — ese 0% es informativo, no evidencia de riesgo real. Filtrar por "algún protocolo falló" (en vez de "DMARC falló") marca como problemáticos remitentes legítimos que nunca se bloquearían ni con `p=reject`. Ya se corrigió una vez (versión inicial usaba OR de fallas individuales) — no reabrir sin este razonamiento.
* **Alertas del dashboard** (`templates/partials/domain_alerts_table.html`, incluido desde `monitoring/dashboard.html`): mismo patrón que remitentes reales — tabla filtrable (`tipo`: todos/remitente_desconocido/cambio_configuracion; `rango`; `q`) y paginada, vía `list_domain_alerts()` en `monitoring_service.py` (reemplazó a `group_unknown_sender_alerts()`, que quedó sin uso y se borró). Remitentes desconocidos se agrupan por organización igual que antes (regex sobre `Alert.message`, no hay columna de organización); el resto de los tipos (cambio de política/SPF/DKIM) no se agrupan, uno por fila. Columna "IP(s)": hasta 3 IPs del grupo + "+N" si hay más — viene de `Alert.related_ip`, que sí es una columna propia (a diferencia de la organización).
  * **Filtros por htmx en la misma página que la tabla de remitentes**: dos `<form>` independientes (`#alerts-filters-form` / `#senders-filters-form`), cada uno con su propio `hx-target`. Los nombres de variable de Jinja NO pueden compartirse entre ambos includes en `dashboard.html` (`rango`/`estado`/`q` ya los usa la tabla de remitentes) — la de alertas usa `alerts_rango`/`alerts_tipo`/`alerts_q` para no pisarlos, aunque el nombre del *parámro HTTP* que manda el form siga siendo `rango`/`tipo`/`q` (eso es independiente, lo define el `name=` de cada input, no el nombre de la variable Jinja). La ruta `monitoring_dashboard` fija la tabla de alertas siempre en su estado default (30d/todos/sin búsqueda) en vez de leerlo de la URL — ninguna de las dos tablas usa `hx-push-url`, así que no hay necesidad real de deep-linking a un filtro particular por URL.
* **Tendencias** (`GET /tendencias`, `GET /tendencias/<access_token>?rango=7d|30d|90d`, `templates/monitoring/trends.html`, ambas `@login_required`): `get_trends_data()` en `monitoring_service.py` arma volumen pass/fail por día y tasa de cumplimiento a partir de `AggregateRecord.count`/`dmarc_aligned` reales — rellena días sin reporte con 0 (pero `compliance_series` queda en `None` esos días, no en `0%`, para no mostrar una falla donde en realidad no hubo tráfico que medir). Gráficos con Chart.js (CDN, solo cargado en esta página vía `head_extra`) — verde `#10b981` para pass/cumplimiento, rojo `#f43f5e` para fail, un solo eje por gráfico. `/tendencias` (sin token) redirige al primer dominio del usuario; `trends_domain` valida el dueño vía `get_owned_domain_or_404()`, igual que el dashboard por token (ver sección Login).
  * **"Emisores que se verían afectados"** (dentro de "Análisis de impacto"): tabla filtrable (buscador) y paginada vía `list_affected_senders()` — reemplazó la lista completa de `get_impact_analysis()["affected_senders"]` (recortada a 20 en el template, sin buscador). `get_impact_analysis()` ya **no** trae esa lista — sólo los agregados (`total_messages`, `pass_rate`, etc.); cualquier código nuevo que la necesite debe llamar `list_affected_senders()` aparte (ya pasó una vez: `domain_health_analysis.py` la usaba para su prompt de IA, ahora recibe `top_affected_senders` como parámetro separado, calculado por la ruta `trends_ai_analysis` con `per_page=5`).
  * **El toggle Cuarentena/Rechazo es JS puro** (`setObjetivoImpacto()`, cambia texto vía `#objetivo-*` ids) y vive **fuera** del partial de la tabla a propósito — si estuviera adentro, cada búsqueda/paginación en la tabla (que sí pega al server y re-renderiza el partial con el texto Jinja por default) resetearía el toggle a "cuarentena" aunque el usuario hubiera elegido "rechazar". Mismo motivo por el que las dos tablas de `monitoring/dashboard.html` usan nombres de variable Jinja distintos entre sí — evitar que un fragmento htmx pise un estado que no le corresponde.
  * `rango` de la tabla de afectados sigue siempre al de la página (no tiene su propio selector 7d/30d/90d) — viaja como `<input type="hidden" name="rango">` dentro del form de filtros, no como pill.
* **Cumplimiento cross-dominio** (`GET /cumplimiento`, `@login_required`): tabla con TODOS los dominios monitoreados del usuario de un vistazo — política DMARC actual, pass_rate de los últimos 30 días, y si "cumple". `get_compliance_overview()` en `monitoring_service.py` la arma en lote (una consulta agregada para pass/fail de todos los dominios + una para la última política de cada uno), no llamando `get_impact_analysis()` en loop — mismo motivo que `get_trends_data`/`list_dmarc_reports`.
  * **Criterio de "cumple" (fijado con el usuario, no reabrir sin razón)**: política ≥ `quarantine` **y** `pass_rate` ≥ `COMPLIANCE_PASS_THRESHOLD` (95%, el mismo umbral que ya usa `list_dmarc_reports()` para marcar un informe "aprobado" — un solo número en toda la app). Sin tráfico en el período: `status = "no_data"`, nunca `"attention"` — no hay evidencia de que algo esté mal, sólo de que no hubo/no llegó tráfico que medir (misma filosofía que `compliance_series` en `get_trends_data`).
  * **DNS en vivo, sin bloquear la tabla**: la carga inicial de `/cumplimiento` sólo usa datos ya guardados (rápido, sin red). La columna "DNS en vivo" de TODOS los dominios llega después con un único fragmento htmx (`GET /cumplimiento/protocolos`, `hx-trigger="load"` sobre el `<tbody>`, swap `outerHTML`) que corre `get_compliance_protocol_status()` — un `run_check()` por dominio, en paralelo con `ThreadPoolExecutor` (mismo patrón que `build_extra_dns_instructions()` en `checkdmarc_service.py`, pero paralelizando entre dominios en vez de entre protocolos de uno solo). `templates/partials/compliance_rows.html` es el `<tbody>` compartido por la carga inicial (con `protocol_status=None`, muestra "Cargando…") y por el fragmento ya resuelto — no duplicar esa tabla en dos templates.

## Login (Flask-Login)

* `models/user.py` (`User`, `UserMixin`): `email` + `password_hash` (werkzeug.security) + `created_at`.
* Rutas gateadas con `@login_required`: `/`, `POST /check`, `GET/POST /monitoreo`, `GET /monitoreos/`, `/cuenta`, `/documentacion`, y **todas** las rutas por `access_token` (`/monitoreo/<token>...`, `/tendencias/<token>...`) — ver más abajo. **No gateada a propósito**: `GET /api/check/<domain>` (API pública, no toca datos de ningún usuario).
  * **`get_owned_domain_or_404(access_token)`** (`app.py`, junto a `admin_required`): resuelve el dominio por token y exige `monitored.user_id == current_user.id` (o `is_admin`) — 404 si no existe o no es dueño, mismo criterio de "no confirmar existencia" que el resto de la app. El dashboard por token **ya NO es un link mágico público** (antes se podía compartir sin cuenta, a propósito) — se sacó esa excepción a pedido explícito: ahora hace falta sesión propia y ser el dueño (o admin) para entrar. Las 12 rutas de dominio (`monitoring_dns`, `monitoring_verify_dns`, `monitoring_verify_tls_rpt`, `monitoring_dashboard`, `monitoring_dashboard_pdf`, `monitoring_dashboard_alerts`, `monitoring_dashboard_senders`, `monitoring_toggle`, `trends_domain`, `trends_affected_senders`, `trends_protocol_status`, `trends_ai_analysis`) llaman este único helper — antes 4 de ellas repetían el mismo chequeo inline (`if not monitored or monitored.user_id != current_user.id: abort(404)`) y las otras 8 no chequeaban nada.
* Perfil de cuenta (`/cuenta`, `/cuenta/correo`, `/cuenta/contrasena`): dos forms independientes; cambiar contraseña exige la actual (`check_password()`), cambiar correo no.
* `@login_manager.unauthorized_handler`: si el destino bloqueado era `/` sin parámetros, redirige a `/ingresar` limpio (sin `?next=%2F`); cualquier otra ruta sí agrega `?next=`.
* `SECRET_KEY`: si falta en el entorno, se genera una al azar en cada arranque (invalida sesiones activas en cada deploy, pero no rompe la app). Definir en Railway para sesiones persistentes.
* **Roles y activar/desactivar cuentas** (`User.is_admin`/`User.is_active`, agregadas con `ALTER TABLE` manual sobre `users` — no son parte del `db.create_all()` original, ver la regla de Base de datos más abajo): `is_active` sobreescribe a propósito la property por default de `UserMixin` (siempre `True`) — es el patrón que la documentación de Flask-Login recomienda para tener cuentas desactivables de verdad.
  * **`@app.before_request` (`reject_deactivated_sessions`)**: desactivar a alguien corta su sesión YA abierta en el siguiente request, no sólo bloquea el próximo login — `login_required`/`current_user.is_authenticated` por sí solos no vuelven a chequear `is_active` en cada request, así que sin este hook una sesión ya iniciada seguiría funcionando igual hasta que la persona cerrara sesión sola. Bug real encontrado y corregido en la misma sesión en que se agregó `is_active` — no reabrir sin este razonamiento.
  * **`/admin/usuarios`** (`app.py`, decorador `admin_required`): panel de administración, sólo para `is_admin=True` — 404 (no 403) a quien no sea admin, mismo criterio que el resto de la app (no confirmar que la ruta existe). Lista de cuentas filtrable (rol, estado, búsqueda) y paginada, mismo patrón htmx que las tablas de remitentes/alertas de `monitoring/dashboard.html`. `services/auth_service.py:list_users()` no agrega en SQL (a diferencia de `monitoring_service.py`) — es una tabla de cuentas de la app, volumen muy chico, no hace falta.
  * **Desactivar una cuenta NO toca sus dominios monitoreados** (decisión explícita) — sigue vigilándose igual; si también hay que pausar dominios, es una acción aparte con el botón que ya existe por dominio.
  * **Dos salvaguardas en `set_user_active()`**: nadie puede desactivarse a sí mismo (`error="self"`), y no se puede desactivar al último admin activo (`error="last_admin"`) — para que la cuenta nunca quede sin ningún admin que pueda revertirlo. Con el hook de arriba ya cortando sesiones de cuentas desactivadas, el caso que el segundo guard cubre es en la práctica casi inalcanzable (un admin necesitaría estar ya desactivado y aun así lograr hacer un request antes de que el hook lo eche) — se deja como defensa en profundidad, no porque sea el mecanismo principal.
  * **No hay self-service para promover/degradar admins todavía** — el primer admin se asignó a mano con un `UPDATE` puntual (`urian.viera@octapus.io`), y cualquier cambio de rol futuro es manual del mismo modo hasta que se construya esa pantalla (decisión explícita: se dejó fuera de esta vuelta a propósito, por ser una acción más sensible que activar/desactivar).
* **Editar el plan de un usuario** (`GET/POST /admin/usuarios/<id>/plan`, `services/monitoring_service.py:get_user_plan_form_data()`/`update_user_plan()`): el admin puede cambiar el `max_domains` y el `expires_at` de cualquier usuario — upsert sobre `UserPlan` (crea la fila si todavía no tenía una propia). `UserPlan.expires_at` se agregó con `ALTER TABLE` manual sobre `user_plans` (la tabla ya existía de antes, vacía en ese momento — no es el `db.create_all()` original de la tabla).
  * **Vencido ≠ bloqueado**: `get_max_domains()` ya lo maneja solo — si `expires_at` quedó en el pasado, vuelve a `DEFAULT_MAX_DOMAINS` en vez de mantener el límite viejo o bloquear todo. Guardar el plan de nuevo (con o sin fecha nueva) lo reactiva — no hace falta borrar la fila a mano para "resetear" un plan vencido.
  * `expires_at` se guarda a las 23:59:59 del día elegido (no a las 00:00) — para que el plan siga valiendo todo ese día, no solo hasta la medianoche anterior.
  * El formulario (`admin/edit_plan.html`) usa el patrón de toast #1 (`render_template` directo, `{% if success/error %}` en `head_extra`) — mismo patrón que `auth/account.html`, no inventar uno nuevo para esta pantalla.
  * La columna "Plan" de `/admin/usuarios` (`services/auth_service.py:list_users()`) importa `get_max_domains()` de `monitoring_service.py` — única dependencia cruzada entre esos dos servicios, en un solo sentido (auth_service → monitoring_service, nunca al revés), para no duplicar la lógica de vencimiento en dos lugares.
* **`User.last_login_at`** (otra columna agregada con `ALTER TABLE` manual sobre `users`): se actualiza en `auth_register`/`auth_login` de `app.py`, justo después de `login_user()` — no en cada request, solo en el momento del login real. `None` = todavía nunca inició sesión (se muestra "Nunca" en `/admin/usuarios`, no una fecha vacía). Sesiones fabricadas a mano para test (`sess['_user_id'] = ...`, ver la sección de comandos en `CLAUDE.md`) no pasan por `auth_login`, así que no actualizan este campo — es esperado, no un bug, si se lo nota en `None` después de probar algo así.
* **API key para consumo externo** (`User.api_key_hash`/`api_key_active`/`api_key_created_at`, 3 columnas más agregadas con `ALTER TABLE` manual sobre `users`; ver `API_PLAN.md` para el resto de la API): mecanismo de auth **separado del login web** — pensado para un consumidor externo (script, otro backend, un frontend propio con o sin framework de JS), no para el navegador.
  * **Por qué SHA-256 y no `generate_password_hash`/`check_password_hash`**: el hash de contraseñas lleva sal aleatoria distinta cada vez a propósito (para que dos contraseñas iguales no se vean iguales en la base) — eso hace *imposible* buscar "¿quién tiene este hash?" directo en una query, habría que comparar contra el hash de cada usuario uno por uno. La API key ya es un token de alta entropía (`secrets.token_urlsafe(32)`), no necesita esa protección extra, así que se guarda su SHA-256 (determinístico: mismo token → mismo hash siempre), permitiendo `User.query.filter_by(api_key_hash=...)` directo. Nunca se guarda la key en texto plano.
  * **`services/auth_service.py`**: `generate_api_key(user_id)` (crea o **regenera** — solo se guarda un hash por usuario, así que regenerar invalida la anterior de inmediato, sin necesitar borrarla a mano) devuelve la key en texto plano, la única vez que existe fuera de la cabeza del usuario — ni la propia app la puede volver a mostrar después. `get_user_by_api_key(raw_key)` (usada por `@require_api_key`) exige `api_key_active` **y** `user.is_active` — una cuenta desactivada tampoco puede seguir usando su key.
  * **`@require_api_key`** (`app.py`, hermano de `@login_required`/`@admin_required`): lee `Authorization: Bearer <key>`, resuelve el usuario en `g.api_user` — a propósito no toca `current_user` de Flask-Login, esto no es una sesión. 401 (no 404) si falta el header o la key no matchea — acá sí conviene confirmar que el mecanismo existe, es una API pensada para integrarse, no una ruta a ocultar.
  * **Generar y desactivar son SOLO de admin, no self-service** (decisión explícita, revertida sobre la versión inicial que sí dejaba generar desde `/cuenta`): `POST /admin/usuarios/<id>/api-key/generar` y `POST /admin/usuarios/<id>/api-key/toggle`, ambas en `admin/edit_plan.html` — el cliente no ve ninguna opción de API key en `/cuenta`. El admin genera la key en nombre del usuario seleccionado (se muestra en texto plano una sola vez, ahí mismo, en su propia pantalla — es quien tiene que hacérsela llegar por fuera de la app) y también es quien la puede pausar. No borra nada, reversible.
  * `GET /api/v1/me` es el primer endpoint real protegido por este mecanismo — sirve de prueba end-to-end del flujo completo; el resto de los endpoints de `API_PLAN.md` se cuelgan del mismo decorador.
  * **Endpoints de dominio** (`/api/v1/dominios`, `/api/v1/dominios/<token>`, `.../remitentes`, `.../alertas`, `.../impacto/afectados`, `.../subdominios`, `.../tendencias`, `.../impacto`, `.../analisis-ia` — resto en `API_PLAN.md`, Fase 2 "en progreso"): todos resuelven el dominio con `get_api_owned_domain(access_token)`. `subdominios`/`tendencias`/`impacto`/`analisis-ia` sólo envuelven `get_subdomain_breakdown()`/`get_trends_data()`/`get_impact_analysis()`/`generate_health_analysis()` en `jsonify()` directo — ya devuelven dicts/listas de `str`/`int`/`float`/`bool`/`None`, sin objetos ORM ni `datetime` sueltos, así que no necesitan pasar por `utils/serializers.py`. `analisis-ia` hace la misma llamada real a OpenAI que ya hacía `trends_ai_analysis` (ninguna llamada nueva agregada, sólo un segundo consumidor del mismo servicio).
  * **`GET /api/v1/cumplimiento`** (cross-dominio, no cuelga de un `access_token`): reusa `get_compliance_overview(g.api_user.id, days)` tal cual — a diferencia de los de arriba, cada fila trae `"monitored"` como objeto ORM (`MonitoredDomain`), así que sí pasa por `serialize_monitored_domain()` antes de responder. No incluye el chequeo de DNS en vivo (`get_compliance_protocol_status()`) — eso es sólo para la UI (columna que carga aparte por htmx en `/cumplimiento`), no tiene sentido en una respuesta JSON síncrona.
  * **`GET /api/v1/informes-dmarc`** (+ `<id>`, cross-dominio): reusa `list_dmarc_reports()`/`get_dmarc_report_detail()` tal cual. `_serialize_dmarc_report_item()` (`app.py`, `item_serializer` de `serialize_paginated()`) es el único mapeo de sus filas (mezclan objetos ORM `report`/`monitored` con campos ya calculados) — lo usan tanto la lista como el detalle, no está repetido. El detalle **no** tiene bypass de admin (a propósito, igual que su equivalente web `dmarc_report_detail`) — no reabrir esa asimetría con los endpoints de dominio por token sin decidirlo aparte.
  * **`GET /api/v1/tls-rpt`**: mismo filtro `estado` que ya usa la página web, en Python sobre `list_domains()` (volumen chico, no vale la pena SQL aparte).
  * **`GET /api/v1/cuenta` NO se implementó como endpoint separado** — se fusionó en `GET /api/v1/me` (que ya devuelve `serialize_user()` con el plan anidado) sumándole sólo `domains_used` (`count_active_domains()`). Un segundo endpoint casi idéntico no daba valor real; ver la nota en `API_PLAN.md`.
  * **`GET /api/v1/admin/usuarios`** (+ `<id>`): sólo para una API key de cuenta admin, vía **`@require_api_admin`** (`app.py`, junto a `require_api_key`) — envuelve a `@require_api_key` en vez de repetir la lectura del header, y devuelve 404 (no 403) a quien no sea admin, mismo criterio que `@admin_required` en las rutas web. La lista reusa `list_users()` tal cual (con su propio `item_serializer` para `serialize_paginated()`, igual patrón que `_serialize_dmarc_report_item`); el detalle no tiene service propio — arma la respuesta a mano con `serialize_user()` + `get_user_plan_form_data()`, mismo patrón que ya usa `admin_edit_plan()` en la ruta web (`User.query.get(user_id)` directo, sin service intermedio, porque no hay lógica de negocio real ahí, sólo lectura).
  * **Rate limit** (`Flask-Limiter`, Fase 3 de `API_PLAN.md`): sólo `/api/check/<domain>` lo tiene (`@limiter.limit("10/minute")`, `default_limits=[]` en la instancia — nada más queda limitado a menos que se decore explícitamente) porque es el único endpoint de la API sin API key, y hace consultas DNS reales por request. Storage en memoria (default de la librería) — alcanza porque la app corre en un solo proceso web (`app.run()`, sin workers/réplicas separadas); si algún día se agregan más procesos hace falta un backend compartido (ej. Redis) para que el límite sea real entre todos. `@app.errorhandler(429)` propio responde JSON (`{"error": "..."}`), nunca la página HTML del 404 — mismo criterio que ya siguen los 404 de la API. (versión API de `get_owned_domain_or_404`, ver sección Login — misma regla `_domain_owned_by()`, comparten la única función con esa lógica, pero esta devuelve `None` en vez de `abort(404)` porque el errorhandler global renderiza HTML, no sirve para JSON) y la ruta responde `jsonify({"error": ...}), 404` a mano. Los 3 endpoints paginados reusan `utils/serializers.py:serialize_paginated()` (misma forma `items`/`total_items`/`page`/`total_pages` que ya devuelve `paginate()`, para no inventar un shape nuevo) y `_parse_rango()` (`app.py`, junto a `TRENDS_RANGE_DAYS`) para el query param `?rango=` — extraído ahí porque las rutas web ya lo repetían inline varias veces y no valía la pena sumar una repetición más.

## Base de datos: Postgres

* `DATABASE_URL` es obligatoria — `app.py` lanza `RuntimeError` si falta, sin fallback local. Railway entrega `postgres://`; SQLAlchemy 2.x solo reconoce `postgresql://` — `app.py` reescribe el prefijo.
* No hay Alembic. `db.create_all()` solo crea tablas nuevas. Con usuarios y datos reales en producción: cualquier columna nueva se agrega con `ALTER TABLE` manual (sintaxis Postgres), nunca borrando tablas. `drop_all()`/cualquier borrado cae bajo la regla de "nunca tocar la base sin autorización explícita".
* Usar siempre tipos de SQLAlchemy dialecto-agnósticos (`db.Boolean`, `db.DateTime(timezone=True)`, `db.JSON`), nunca SQL crudo específico de un motor.
* Si se agrega un `.delete()`, usar `db.session.delete(instancia)`, no `Query.delete()` en bloque, para que el `cascade` funcione.
